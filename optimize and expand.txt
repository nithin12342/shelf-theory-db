### 2. Deep Technical Breakdown of Each Problem



#### 2.1 Problem 1: Durable Single-Row Writes (Lost to SQLite by 4.06x)

**Operational Context:** Real-time online transaction processing (OLTP) where an application writes single records with durable disk synchronization.
**Measured Evidence:** SQLite completed single durable inserts in **1.70 &mu;s** at median. ShelfDB required **6.90 &mu;s** at median ([DETAILED_LOSS_ANALYSIS_2026-10-23.md](file:///d:/d2/DETAILED_LOSS_ANALYSIS_2026-10-23.md#L44-L64)). SQLite ran 4.06 times faster.
**Architectural Root Cause:** 
  1. SQLite writes raw records into 4 KB database page caches with a single mutex.

  2. ShelfDB writes multi-dimensional cell descriptors. It serializes discrete attributes, continuous float embedding stalks, and boundary incidence links.

  3. ShelfDB computes an explicit CRC32C checksum across every frame header and synchronizes the write-ahead log file.

**Engineering Verdict:** This is a permanent structural trade-off. ShelfDB will not beat SQLite on single-row scalar inserts.


#### 2.2 Problem 2: Raw Relational Joins Without Fiber Bundles (Lost to DuckDB by 15.8x)

**Operational Context:** Ad-hoc analytical queries across flat, un-indexed tables without prior topological compilation (for example, joining raw TPC-H lineitem and orders tables).
**Measured Evidence:** DuckDB executed the three-table join over 6,001,215 rows in **158.30 ms**. ShelfDB without a pre-compiled fiber bundle required **2,500.00 ms** ([DETAILED_LOSS_ANALYSIS_2026-10-23.md](file:///d:/d2/DETAILED_LOSS_ANALYSIS_2026-10-23.md#L67-L86)). DuckDB ran 15.79 times faster.
**Architectural Root Cause:**
  1. DuckDB compiles vectorized radix hash tables in parallel across all CPU cores and probes them with vector instructions.

  2. ShelfDB does not contain a dynamic relational hash-join compiler.

  3. ShelfDB achieves speed by pre-folding boundary connections into topological cell complexes.

  4. When an un-indexed flat join executes, ShelfDB falls back to generic nested loops.

**Engineering Verdict:** Architectural boundary. When you pre-materialize fiber sections, ShelfDB wins in 3.7 ms. On raw flat tables without fiber bundles, DuckDB wins decisively.


#### 2.3 Problem 3: Analytical Scans with a Single Accumulator (Lost to DuckDB by 1.36x)

**Operational Context:** High-throughput sequential scans that aggregate a single column over millions of rows.
**Measured Evidence:** DuckDB scanned 6,001,215 lineitem rows in **5.60 ms**. The baseline ShelfDB scan required **7.60 ms** ([DETAILED_LOSS_ANALYSIS_2026-10-23.md](file:///d:/d2/DETAILED_LOSS_ANALYSIS_2026-10-23.md#L88-L108)). DuckDB was 1.36 times faster.
**Architectural Root Cause:**
  1. The baseline ShelfDB loop updated one CPU register accumulator (`acc += stalk[i]`).

  2. Each addition waited for the previous addition to retire. This dependency chain stalled the CPU pipeline.

  3. DuckDB avoided stalls by processing chunks with AVX2 vector instructions.

**Engineering Remedy:** We unrolled the inner scan into four independent accumulators in [`fused_scan_bench.rs`](file:///d:/d2/sheaf-db/crates/sheaf-engine/src/bin/fused_scan_bench.rs). This eliminated pipeline stalls and reduced ShelfDB query time to **4.00 ms**, beating DuckDB by 1.40 times.


#### 2.4 Problem 4: Cold Ingest and Setup Latency (Lost to All Engines by 26x to 511x)

**Operational Context:** Loading raw text files (CSV or TSV) from disk into the database for the first time.
**Measured Evidence:** SQLite loaded the IMDb dataset in **1.91 s**. DuckDB loaded tables in **0.10 s to 156.00 s**. ShelfDB required **51.10 s to 112.72 s** to build the fiber bundle ([ADVERSARIAL_ANALYSIS.md](file:///d:/d2/ADVERSARIAL_ANALYSIS.md#L43-L60)).
**Architectural Root Cause:**
  1. Relational databases parse text lines and append binary rows directly into storage pages.

  2. ShelfDB executes heavy mathematical compilation at load time.

  3. The engine parses lines, builds a graded cell poset, evaluates dual stalks, verifies boundary chains ($\delta^2 = 0$), sorts fiber sections, and seals CRC checksums.

**Engineering Verdict:** ShelfDB trades load time for query time. If you run one query on a dataset once, the competing databases win on total time. If you run repeated queries, ShelfDB amortizes the build time.


#### 2.5 Problem 5: Pure 1D Vector Array Slice Filtering (Lost to Kdb+ by 4.8x)

**Operational Context:** In-memory numerical time-series range filtering over contiguous timestamp arrays.
**Measured Evidence:** On 100,000 tick records, the internal Kdb+ q engine executed a 1-hour time slice filter in **10.00 &mu;s**. ShelfDB executed the same slice filter in **48.00 &mu;s** ([KDB_TIMESERIES_COMPARISON_2026-10-27.md](file:///d:/d2/KDB_TIMESERIES_COMPARISON_2026-10-27.md#L97-L115)). Kdb+ was 4.80 times faster.
**Architectural Root Cause:**
  1. Kdb+ stores time-series data as flat, memory-mapped vectors with no cell wrappers.

  2. The q vector interpreter applies vector instructions directly to homogeneous numeric arrays.

  3. ShelfDB stores multi-dimensional cells with discrete payloads, stalk buffers, and offset indices. Scanning cell headers introduces memory overhead compared to pure flat numeric arrays.

**Engineering Verdict:** For pure 1D numeric vectors without relational joins or continuous harmonic solves, Kdb+ remains faster.
